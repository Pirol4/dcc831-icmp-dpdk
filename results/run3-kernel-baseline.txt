Kernel-echo baseline: the SERVER's Linux kernel answers the ping (icmp-echo
stopped, 192.168.1.3/24 assigned to eno1d1 on node-0). Same link, same client.

server setup (node-0):
  sudo ip addr add 192.168.1.3/24 dev eno1d1
  sudo sysctl -w net.ipv4.icmp_echo_ignore_all=0
  eno1d1  UP  192.168.1.3/24

=== sudo ping -f -w 15 192.168.1.3  (client, node-1) ===
PING 192.168.1.3 (192.168.1.3) 56(84) bytes of data.

--- 192.168.1.3 ping statistics ---
546855 packets transmitted, 546855 received, 0% packet loss, time 15000ms
rtt min/avg/max/mdev = 0.011/0.017/0.450/0.007 ms, ipg/ewma 0.027/0.018 ms

=== comparison ===
                       flood RTT min / avg / max        server-side work
  DPDK echo server     7 µs / 10 µs / 424 µs            303 ns  (measured, TSC)
  kernel echo server   11 µs / 17 µs / 450 µs           ~4-7 µs (inferred, RTT delta)

  RTT delta (kernel - DPDK):  min +4 µs,  avg +7 µs
  => a full Linux network-stack traversal on the server for one ICMP echo
     costs ~4 µs (best case) to ~7 µs (typical): IRQ/NAPI -> netif_receive_skb
     -> ip_rcv -> icmp_rcv -> icmp_echo -> icmp_reply -> ip_output ->
     dev_queue_xmit -> mlx4 xmit. The DPDK app does the same job in 0.3 µs.

Note on packet rate: both floods are limited by the *client* ping process
(one sendto()+recvmsg() round trip per packet, ~20-40 µs of client CPU each),
not by either server, so the transmitted-packet counts (353k vs 547k) reflect
client-side scheduling noise, not server throughput.
